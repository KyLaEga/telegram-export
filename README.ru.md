# 📥 Telegram Media Exporter

Потоковый экспорт медиа из каналов и чатов Telegram **напрямую на внешний SSD** под macOS. Рассчитан на большие объёмы — терабайт и выше — без раздувания оперативной памяти и без износа встроенного накопителя Mac.

---

## 1. Общая архитектура и концепция

Скрипт `export_media.py` — это однофайловый загрузчик на базе [Pyrogram](https://docs.pyrogram.org/), решающий одну задачу: **выгрузить всё медиа целевого канала на внешний диск, надёжно и идемпотентно**, переживая обрывы связи, FloodWait'ы и перезапуски.

### Zero-In-Memory I/O

Ключевая особенность — **потоковая запись минуя память и системный кэш**. Сетевые пакеты по мере приёма (чанками по 1 МБ) пишутся сразу в файл на внешнем SSD:

```
Telegram (MTProto) ──► chunk 1 МБ ──► файл на /Volumes/SSD/...
                       (в память не накапливается)
```

Это даёт три эффекта:

| Эффект | Почему важно |
| --- | --- |
| **Нет роста RAM** | Файл на 50 ГБ не пытается уместиться в память — пишется потоково. |
| **Обход песочницы App Store** | Запись идёт напрямую на смонтированный том `/Volumes/...`, минуя ограничения sandbox. |
| **Экономия ресурса встроенной SSD Mac** | Данные не оседают на системном диске промежуточным кэшем — циклы перезаписи (TBW) внутреннего накопителя не расходуются. |

### Возможности

- **Идемпотентность** — повторный запуск пропускает готовые файлы, докачивает частичные, перекачивает повреждённые.
- **Дедупликация по содержимому** — один и тот же файл из разных сообщений скачивается один раз.
- **Двухпроходная резолюция качества** — из нескольких версий одного ролика/файла качается только лучшая (самая крупная), худшие отсекаются ещё до записи на диск (см. [раздел 4](#4-механизмы-защиты-ssd-и-дедупликация)).
- **Файловая система как источник правды** — сверка по реальным байтам на диске, а не по хрупким текстовым кэшам (см. [раздел 4](#4-механизмы-защиты-ssd-и-дедупликация)).
- **Многопоточная загрузка** — крупные файлы качаются в несколько соединений одновременно.
- **Автоперехват FloodWait** и автопродолжение после разрыва связи.
- **Предпросмотр** — сколько файлов и сколько ГБ предстоит скачать + оценка времени.
- **Режим аудита** (`--verify`) — проверка целостности без скачивания.
- **Комиксы и файлы по ссылкам** (`--links`) — помимо медиа, *прикреплённого* к сообщению (фото/видео/документы, в т.ч. присланные файлом `.pdf`/`.cbz`), качает содержимое по **внешним ссылкам** (превью web-страниц и URL в тексте): прямые файлы (`.pdf`/`.cbz`/`.zip`/картинки) — как есть, а страницы-галереи парсятся и собираются в один комикс в формате **CBZ** или **PDF** (`--links-format`). Всё кладётся в подпапку `comics_and_links/` и пропускается, если уже скачано.

## 2. Подготовка среды

### ⚠️ Требование: Python 3.12

Скрипт работает **только на Python 3.12**.

> **Python 3.13 не поддерживается** — Pyrogram и `tgcrypto` (C-расширения для ускорения шифрования MTProto) на момент написания не собираются под 3.13. Установка строго на 3.12.

Проверьте версию:

```bash
python3.12 --version
# Python 3.12.x
```

### Установка зависимостей

```bash
# Рекомендуется виртуальное окружение
python3.12 -m venv venv
source venv/bin/activate

pip install pyrogram tgcrypto
```

| Пакет | Назначение |
| --- | --- |
| `pyrogram` | Клиент Telegram MTProto (логин, история, стриминг медиа). |
| `tgcrypto` | Нативное ускорение шифрования — без него загрузка в разы медленнее. |

### Получение API_ID и API_HASH

Скрипту нужны личные API-ключи Telegram (одноразово):

1. Откройте **<https://my.telegram.org>** и войдите по номеру телефона.
2. Перейдите в раздел **API development tools**.
3. Создайте приложение (поля `App title` / `Short name` — любые).
4. Скопируйте два значения:
   - **`api_id`** — число (например `1234567`).
   - **`api_hash`** — строка из 32 символов.

Эти ключи понадобятся при первом запуске. Храните их приватно — это доступ к вашему аккаунту.

## 3. Управление через CLI

### Стандартный запуск

```bash
python3.12 export_media.py
```

При **первом старте** скрипт проведёт интерактивную настройку: спросит `API_ID`, `API_HASH`, номер телефона, ссылку на канал и предложит выбрать том SSD из подключённых. Конфигурация сохраняется в `config.json` (права `600`), сессия — в `tg_export_session.session`.

При **последующих стартах** настройки берутся автоматически, и скрипт сразу:

1. Дочитывает новые сообщения канала (инкрементально, по кэшу ID).
2. Синхронизирует индекс с диском.
3. Показывает предпросмотр (объём к загрузке + оценка времени).
4. Качает медиа потоком, **автоматически продлеваясь** после обрывов связи и пережидая FloodWait.

Прервать можно `Ctrl-C` в любой момент — прогресс сохраняется, перезапуск продолжит с места.

### Все режимы и флаги

| Флаг | Назначение |
| --- | --- |
| *(без флагов)* | Стандартный потоковый экспорт с автопродолжением. |
| `--verify` | **Аудит (Dry Run)** — проверка целостности без скачивания, см. ниже. |
| `--rescan` | Сброс кэша сообщений — быстрый пересбор истории канала с нуля. |
| `--reset` | Сброс конфигурации и сессии (привязка нового аккаунта / смена SSD). |
| `--workers N` | Число параллельно качаемых файлов (по умолчанию `1` при многопотоке, иначе `3`). |
| `--connections N` | Соединений на один файл в многопотоке (по умолчанию `8`). |
| `--no-fast` | Отключить многопоток — качать каждый файл одним потоком. |
| `--no-dedup` | Отключить дедупликацию по содержимому. |
| `--no-quality` | Отключить двухпроходную резолюцию качества — качать все версии дублей, а не только лучшую. |
| `--only T1,T2` | Качать только указанные типы. |
| `--skip T1,T2` | Пропускать указанные типы. |
| `--links` | Дополнительно качать комиксы/файлы по **ссылкам** из сообщений (web_page + URL в тексте), а не только прикреплённое медиа. |
| `--links-format {cbz,pdf}` | Формат сборки комиксов из страниц-галерей (по умолчанию `cbz`). |

Доступные типы для `--only` / `--skip`:
`video`, `document`, `audio`, `voice`, `animation`, `video_note`, `photo`.

### Режим аудита `--verify`

```bash
python3.12 export_media.py --verify
```

Изолированный **Dry Run**: скрипт **не скачивает** ни одного байта медиа. Он сканирует папку назначения, сверяет каждый файл из плана с реальным состоянием на диске и формирует отчёт `verify_report.txt` со статусами:

| Статус | Значение |
| --- | --- |
| `[COMPLETE]` | Файл на месте, размер байт-в-байт совпадает с серверным. |
| `[PARTIAL]` | Файл есть, но недокачан (размер меньше эталона). |
| `[MISSING]` | Файла нет на диске. |
| `[OVERSIZE]` | Файл больше эталона — признак повреждения. |

Используйте перед архивацией или после массовой загрузки, чтобы убедиться, что **скачано действительно всё**. Дальнейшую докачку запускайте обычным прогоном (без флага).

### Сброс кэша `--rescan`

```bash
python3.12 export_media.py --rescan
```

Принудительно очищает локальный индекс ID и метаданных (`.tg_export_ids.json`, `.tg_export_meta.json`) и проходит историю канала **с нуля** быстрым проходом. Применяйте, если старая база ID повредилась, «зависла» или канал был сильно перелопачен (удаления/перезаливки). Скачанные файлы при этом **не трогаются**.

### Сброс конфигурации `--reset`

```bash
python3.12 export_media.py --reset
```

Удаляет локальный `config.json` и (по подтверждению) файл сессии. Нужен, чтобы **привязать другой аккаунт**, сменить целевой канал или **путь к SSD**. После сброса следующий запуск снова запустит интерактивную настройку.

## 4. Механизмы защиты SSD и дедупликация

Главный принцип: **источник правды — сама файловая система, а не текстовые кэши.** Манифест и индексы — лишь ускоряющий слой; решения о (не)скачивании принимаются по реальным байтам на диске.

### `reseed_manifest_from_disk` — синхронизация с диском

Текстовый манифест дедупликации (`.tg_export_manifest.json`) может потеряться или повредиться. Раньше это привело бы к повторной закачке всех дубликатов. Теперь при каждом старте (до начала загрузки) скрипт:

1. Сканирует папку назначения и находит все файлы вида `msg_<id>_<имя>`.
2. Читает их **реальный размер в байтах** прямо с SSD.
3. На лету восстанавливает индекс дедупликации в памяти, дополняя его завершёнными файлами.

```
.tg_export_manifest.json  ──┐
                            ├──► индекс дедупа в RAM
реальные файлы на SSD ──────┘   (диск имеет приоритет)
```

В результате потеря манифеста больше **не приводит** к перекачке — диск самодостаточен.

### Политика перезаписи (защита TBW)

Каждый файл перед обработкой классифицируется по сверке размера, и действие выбирается так, чтобы **минимизировать циклы перезаписи** накопителя:

| Состояние файла на диске | Действие | Запись на SSD |
| --- | --- | --- |
| Размер совпал (`COMPLETE`) | **Жёсткий пропуск** | ❌ нет |
| Файл недокачан (`PARTIAL`) | **Только докачка** с места обрыва | ✅ только хвост |
| Файл больше эталона (`OVERSIZE`) | Перезапись с нуля | ✅ полная |
| Файла нет (`MISSING`) | Скачивание | ✅ полная |

Ключевые гарантии:

- **Готовые файлы не трогаются** вообще — ни перезаписи, ни даже открытия на запись.
- Перезапись с нуля инициируется **только** для повреждённых (`OVERSIZE`) файлов.
- Файлы, не относящиеся к экспорту (без префикса `msg_<id>_`), **никогда не удаляются** автоматически.

### Дедупликация по содержимому

Дубликатом считается **полное совпадение имени и размера** в байтах (а для видео — ещё и длительности). Это намеренно строгая проверка: в каналах полно разных роликов с одинаковыми именами (`video.mp4`, `IMG_1234.mp4`), и группировать только по имени нельзя. Один и тот же файл, репостнутый в нескольких сообщениях, скачивается **один раз**.

### Двухпроходная резолюция качества (Two-Pass Quality Resolution)

Дедупликация выше отсекает лишь *байт-в-байт идентичные* копии. Но в каналах один и тот же ролик часто перезаливают в **разном качестве** — одинаковое имя и длительность, но разный размер. Качать их все — пустая трата ресурса перезаписи (TBW) SSD. Эта фаза выбирает из каждой такой группы **только лучшую версию**.

Механизм работает на **pre-flight** этапе — до единого обращения к диску — в два прохода:

1. **Сбор отпечатков.** Для каждого медиа из плана строится «цифровой отпечаток» (`fingerprint`), в который **намеренно не входит размер**:
   - видео: `(тип, имя_файла, длительность)`
   - фото/документы: `(тип, имя_файла)`
2. **Quality Clash.** Сообщения с одинаковым отпечатком группируются, и внутри группы сравнивается `file_size`:
   - файл с **максимальным размером** объявляется «Мастер-файлом» и ставится в очередь на загрузку;
   - остальные версии помечаются как дубликаты низкого качества и **исключаются из плана ещё до записи на диск**.

```
msg_101  clip.mp4  120с   50 МБ ─┐
msg_102  clip.mp4  120с  200 МБ ─┼─► отпечаток (video|clip.mp4|120) ─► Мастер: msg_102 (200 МБ)
msg_103  clip.mp4  120с   80 МБ ─┘     msg_101, msg_103 — пропущены
```

Судьба каждой пропущенной версии фиксируется в **`quality_report.txt`**:

```
Файл msg_101 пропущен. Выбран дубликат лучшего качества: msg_102 (Размер: 190.73 MB)
Файл msg_103 пропущен. Выбран дубликат лучшего качества: msg_102 (Размер: 190.73 MB)
```

Фаза включена по умолчанию; отключается флагом `--no-quality`. Она дружит с остальными механизмами:

- **`--verify`** — аудит выполняется уже по мастер-файлам, а `quality_report.txt` формируется и в режиме Dry Run.
- **`reseed_manifest_from_disk`** — резолюция лишь сужает план до мастеров; восстановление индекса дедупа с диска работает поверх и независимо. Файлы худших версий, уже лежащие на диске с прошлых прогонов, **не удаляются** — механизм только не даёт скачивать их заново.

## 💡 Практические заметки

- **Файловая система SSD.** Для файлов крупнее 4 ГБ нужен **exFAT** или **APFS** — на FAT32 такие файлы записать невозможно (скрипт предупредит).
- **Тротлинг Telegram.** Аккаунт может быть ограничен по скорости (наблюдалось ~5 МБ/с). При флуд-вейтах оптимальнее **меньше агрессии**: `--connections 4 --workers 1`.
- **Защита от заполнения диска.** Перед каждым файлом проверяется свободное место с запасом 2 ГБ; при нехватке загрузка аккуратно останавливается.

```bash
# Пример «бережного» запуска под лимитированный аккаунт
python3.12 export_media.py --connections 4 --workers 1
```
